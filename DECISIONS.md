# DECISIONS.md

## Вариант

Номер варианта: 4 (две последние цифры зачетки 25Т0859: 59 mod 8 + 1 = 4).

Изменяемый аспект: новый канал, параметр 25.
Как применен параметр: по пункту 5 задания нужно добавить индивидуальный канал, поэтому параметр относится
к новому каналу. Это PUSH, push-уведомление на устройство. Текст push-уведомления виден в баннере только
коротким, поэтому 25 - это максимальная длина текста.
Правило, которое реализовано: PUSH принимает запрос, если адресат - токен устройства без пробелов и текст
не длиннее 25 символов. "Report is ready, check it" (25) отправляется, с восклицательным знаком (26) - нет.

Где сосредоточено: класс PushChannel и его константа MAX_LENGTH = 25. Для нового канала понадобились этот класс,
константа PUSH в enum ChannelType и одна строка регистрации в конструкторе ChannelFactory. EmailChannel,
SmsChannel, InternalChannel и NotificationService не менялись.

## Решение 1. Каждый канал сам проверяет своего адресата

Формулировка: у интерфейса NotificationChannel два метода, supports и send. EmailChannel проверяет один @,
непустое имя и точку в домене, SmsChannel проверяет формат +7 и 10 цифр, InternalChannel - что адресат не пустой,
PushChannel - токен без пробелов и длину текста. NotificationService проверяет только общие данные запроса
(тип есть, текст не пустой) и вызывает supports и send у выбранного канала.

Альтернатива: все проверки адресатов в сервисе в switch по типу.

Обоснование: правила адресата у каналов разные, и место им рядом с отправкой этого канала. Тогда сервис
не знает деталей ни одного канала, а новый канал приносит свою проверку с собой.

## Решение 2. Фабрика передается в сервис через конструктор

Формулировка: NotificationService получает ChannelFactory в конструкторе и сам каналы не создает.
ChannelFactory хранит каналы в EnumMap и только отдает нужный по типу. У фабрики два конструктора:
обычный регистрирует четыре настоящих канала, второй принимает свою Map каналов.

Альтернатива: new EmailSender() и подобные прямо внутри метода отправки, как в исходной версии со switch.

Обоснование: когда зависимость приходит снаружи, ее можно подменить. В SelfCheck сервис собирается с фабрикой,
в которой вместо EmailChannel стоит заглушка FakeChannel, и проверяется, что send вызывается ровно один раз
для правильного адресата и ни разу для неправильного, без настоящей отправки.

## Какие изменения стали локальными

После переработки новый канал - это новый класс, константа в enum и строка в фабрике. Изменение правила адреса
email затрагивает только EmailChannel. Изменение общих проверок запроса затрагивает только NotificationService.
Замена способа отправки для тестов делается без правки кода, через второй конструктор фабрики.

## Результаты граничных проверок

- типовое значение: data/sample.csv - все три уведомления (EMAIL, SMS, INTERNAL) отправлены
- граница email: a@b.c принимается, user@localhost (нет точки), user@example. (точка в конце), без @, с двумя @ - нет
- граница SMS: +79990000000 (10 цифр после +7) принимается, 9 и 11 цифр, 8 вместо +7, буква - нет
- граница PUSH по варианту: текст 25 символов отправлен, 26 - нет; токен с пробелом и пустой - нет
- пустое значение: пустой текст - "пустой текст сообщения", адресат из пробела для INTERNAL - отказ, запрос null - ошибка
- неверный формат: канал FAX и строка из 2 полей - ошибка в строке файла
- конфликт: фабрика без канала SMS на запрос SMS бросает IllegalArgumentException

Все проверки есть в SelfCheck (28 PASS), строки для файла лежат в data/boundaries.csv.

## Собственные формулировки

### Какая проверка защищает от наиболее вероятной ошибки входных данных

Самая вероятная ошибка - адресат не в том формате для выбранного канала: телефон с 8 вместо +7, email без
домена. Ее ловит supports конкретного канала, а NotificationService при отказе возвращает
NotificationResult(false, ...) и не вызывает send. Пустой текст сообщения проверяется раньше, в самом сервисе,
потому что это правило общее для всех каналов.

### Какой метод или класс содержит ключевое бизнес-правило и почему

Правило моего варианта - ограничение 25 символов для PUSH. Оно в PushChannel.supports и константе MAX_LENGTH.
Оно относится только к push-уведомлениям, поэтому лежит в их классе, а другие каналы о нем не знают.

### Как Activity-диаграмма отражает участок кода

Блок A1 "Проверить общие данные запроса" - первые проверки в NotificationService.notify: запрос и тип не null,
текст не пустой. "Выбрать NotificationChannel" - factory.get(r.type()). Ромб "Канал поддерживает адресата" -
if (!c.supports(r)), ветка "нет" - return new NotificationResult(false, ...). "Отправить через общий интерфейс" -
return c.send(r), здесь сервис не знает, какой класс стоит за c.

### Какое изменение требования затронет минимум классов

Изменение длины push-уведомления меняет одну константу MAX_LENGTH в PushChannel. Изменение формата номера SMS
меняет одну регулярку в SmsChannel. Сервис и фабрика при этом не меняются.

## Фрагмент кода для анализа

switch (type) { case EMAIL -> new EmailSender().send(...); case SMS -> new SmsSender().send(...); } создает
конкретные классы прямо в месте отправки. Сервис из-за этого знает про все способы отправки, при новом канале
этот switch надо переписывать, а для проверки нельзя подставить заглушку: всегда создается настоящий отправщик.
Это нарушает правило, что сервис не знает деталей каналов. В моем проекте сервис вызывает
factory.get(r.type()), а фабрика приходит в конструкторе.
